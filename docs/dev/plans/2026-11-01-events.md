# Plan: events and push

Status: design, revised after the owner's review of 2026-11-01 (webhooks come from one background server and are
set in each tool's config). Nothing here is built. The measurement behind it is in cli-testing
([`performance/events/change-detection`](https://github.com/WireCatLabs/cli-testing/blob/main/performance/events/change-detection/README.md),
[cli-testing#281](https://github.com/WireCatLabs/cli-testing/pull/281)).

## Why

The owner (2026-11-01): "we need to watch and push changes on change to desktop if it's open. I think we need a
proper push system so the changes can be actually pushed and notifications can come etc. … so it's possible to
subscribe to core events in clis, to the events from outside and so on".

The first need is concrete. WireCat Desktop's Memory page, and the Tasks page its plan describes, must update when
an agent or another CLI changes a task, a memory or a fact. Today the page loads once and has a Refresh button.

After that, the same events must reach:

- other CLIs and agents on this computer;
- other servers and apps, as signed webhooks;
- the owner, as an OS notification or a message in a messenger;
- and the bus must take events *from* outside: Telegram bot updates, Gmail and Drive change signals, other apps.

## Summary

1. **One `events` table in `wirecat.db`, written by SQL triggers** in the same transaction as the change. A trigger
   is part of the database file, so every build of every CLI that writes the migrated store emits events, including
   CLIs released before this one.
2. **An event holds references, never content:** a sequence number, a type (`task.status`), a ref (`task:12`), the
   actor, and the names of the changed fields. Readers fetch current state through the commands they already use.
3. **One events server per user**, shared by every tool. Any cli-core command that writes the store, and every
   `mcp serve`, starts it detached if it is not running; the command never waits for it. Once started it keeps
   running, and a "Start at login" switch on the desktop's Tools page brings it back after a reboot. It delivers webhooks from
   the log with retries, receives inbound events, and serves local subscribers over a socket (a named pipe on
   Windows). It is the only process that polls the store for them.
4. **Readers learn of changes by polling `PRAGMA data_version` every 250 ms**: measured 1.3 µs per check, no missed
   commit. `<tool> events watch --since <seq> --json` prints NDJSON; it attaches to the server when one runs and polls
   on its own when none does, so it always works, also with no server. The desktop uses it and never delivers.
5. **Webhooks are set in each tool's config** (`webhooks.<name>`: url, events, enabled) through `<tool> webhooks …`
   commands, which the desktop's Tools panel calls from a Webhooks block beside Permissions. The signing secret
   lives in that tool's keyring entry and is never printed. Delivery follows Standard Webhooks.

### Prior art: beads

Beads keeps an "events journal": one row per committed mutation, written in the same transaction, with a gapless
`seq`, read by `bd events tail --since <seq> [--follow]` and over HTTP as `GET /v0/beads/events:watch` (server-sent
events, `id: <seq>`, heartbeats every 20 s, a `410` and a `truncated` event when the cursor fell below what pruning
kept) ([events-journal.md](https://github.com/gastownhall/beads/blob/6ebaacba8f5fb1f5005eed0544f26f3a7a58a5e4/docs/reference/events-journal.md)).
Three things carry over:

- **Its push is a poll underneath.** `--follow` "polls once a second", and the HTTP stream re-reads on a jittered
  timer ([events_watch.go](https://github.com/gastownhall/beads/blob/6ebaacba8f5fb1f5005eed0544f26f3a7a58a5e4/internal/httpapi/events_watch.go)).
- **`--exit-on-stdin-eof`** so a desktop parent that dies takes the follower with it.
- **A warning:** each record carries the full issue snapshot, so "publishing the journal publishes the workspace's
  history … editing or deleting a bead does not redact it". This plan keeps content out of the log for that reason.

### Producing events

| Option | Every writer emits? | Old CLI builds emit? | Actor | Cost | Verdict |
|---|---|---|---|---|---|
| **A. No log: the desktop reloads when the store changes** (`data_version` moved) | yes | yes | none | nothing to build in core | **No.** During a sync the store changes on nearly every check: 228 of 405 checks at 50 ms saw a commit with no task event in the measurement. The page would reload all through a sync, and webhooks and resume need a log anyway |
| B. App inserts an event row in each store method, inside `write()` | only paths that remember to; `setStatus` runs outside `write()` | **no**: a tg-cli on an older core writes tasks with no event | exact | one line per write path, about 25 places | No: misses writes by the six CLIs released at different times |
| **C. SQL triggers on the tables that matter** | yes, any connection | **yes**, once any CLI migrates the store | from the row (`task_events.actor_*`, `memories.author_*`, `facts.confirmed_by_*`); none for a bare claim | one migration | **Recommended** |
| D. Extend `task_events` to cover everything | tasks only | yes | yes | — | No: memories and facts are not tasks |
| E. `sqlite3_update_hook` | only the connection that set it | no | — | — | No: the hook belongs to one connection ([SQLite docs](https://www.sqlite.org/c3ref/update_hook.html)); other processes' writes are not reported (inferred from "the database connection identified by the first argument") |

Option C's limit: a trigger cannot learn who acted unless the row says so. A non-TEMP trigger cannot read a
per-connection TEMP table ([CREATE TRIGGER](https://www.sqlite.org/lang_createtrigger.html): "the table to be
modified or queried must exist in the same database"), and an app-defined SQL function would break every older
build that fires the trigger. The rows already carry an actor for the changes that matter most (task events, memory
authors, fact confirmations). Where they do not, `actor` is null and means "unknown", as in beads.

## Recommendation

### The event log

Migration 42 (reserved first in `docs/dev/COORDINATION.md`) adds, additively, with no change to `minCompatible`:

```sql
CREATE TABLE events (
  seq INTEGER PRIMARY KEY AUTOINCREMENT,  -- never reused, even after pruning
  type TEXT NOT NULL,                     -- 'task.status', 'memory.added' …
  subject_type TEXT NOT NULL,             -- 'task' | 'memory' | 'fact' | 'agent_action' | 'inbound'
  subject_id INTEGER NOT NULL,
  actor_type TEXT,                        -- 'person' | 'bot' | null (unknown)
  actor_id INTEGER,
  fields TEXT,                            -- JSON array of changed column names; never values
  at INTEGER NOT NULL                     -- ms
);
```

`AUTOINCREMENT` matters: without it, the rowid of a deleted newest row "might be reused", and a reader's cursor must
never point at a different event ([AUTOINCREMENT](https://www.sqlite.org/autoinc.html)). SQLite lets one writer in
at a time, so `seq` order is commit order: a reader never sees seq 10 while seq 9 is still uncommitted, the gap that
makes outbox cursors hard on Postgres (inferred from the one-writer rule in the [WAL docs](https://www.sqlite.org/wal.html);
AUTOINCREMENT promises increasing numbers, not consecutive ones, so readers never expect `seq + 1`). `store_settings` gets an
`events_store_id`, a random id written once by the migration; it names this file's sequence.

Triggers, each `AFTER … FOR EACH ROW`, and for updates `UPDATE OF <the columns a person sees>` plus
`WHEN old.x IS NOT new.x`, so the folded-name fills, backfills and pruning that run on every writable open
(`src/store/sqlite/open-store.ts:74-88`) do not flood the log:

| Trigger on | Event type | Actor |
|---|---|---|
| `task_events` INSERT | `task.<kind>` (`task.created`, `task.status`, `task.assigned` …); `fields` = the keys of `changes` via `json_each`, never the values | `task_events.actor_*` |
| `tasks` UPDATE OF `claimed_by`, `claimed_until` | `task.claimed` / `task.released` | null (the holder is a free-text name, not an actor) |
| `tasks` UPDATE OF `resolution`, `verdict`, `close_certainty` | `task.updated` with `fields` | null |
| `tasks` DELETE | `task.removed` | null |
| `memories` INSERT / UPDATE OF `body`, `kind`, `status`, `scope`, `subject_*`, `deleted_at` / DELETE | `memory.added` / `memory.updated` / `memory.removed` | `author_*` on insert |
| `facts` INSERT / UPDATE OF `statement`, `status`, `type`, `project_id` / DELETE | `fact.added` / `fact.updated` / `fact.removed` | `confirmed_by_*` when set |
| `proposed_actions` INSERT / UPDATE OF `status`, `verdict` | `action.proposed` / `action.updated` | `proposed_by_*` / `decided_by_*` |
| `agent_actions` INSERT | `agent.action` | the row's actor |

These cover all four lists of the Memory page (`memories`, `facts`, `actions`, `agents list`). A memory that became
a fact got `deleted_at` only from a one-time migration (`migrations.generated.ts:326`); the column is in the list in
case a live path ever sets it. **Task tags are not covered:** tagging changes neither `task_events` nor `tasks`, so
the Tasks page will need a trigger on the tag links (RISK, before that page ships).

Notes, reminders, documents, messages and chats are not in the first set. Messages change thousands of times during a
sync and already have their own `changes` read; a message event type would come with its own volume budget later.

### The record a reader sees

```json
{"seq":4212,"type":"task.status","ref":"task:12","actor":"bot:3","fields":["status"],"at":"2026-11-01T10:04:05.120Z"}
```

- `ref` is the same ref every command already takes (`memory:7`, `task:12`). A reader that wants the title runs
  `tasks show task:12`, under its own permissions.
- `fields` tells a page which column to refresh and lets a filter skip noise, without carrying a value.
- **Privacy:** no titles, bodies, statements, message text, URLs or names. A log that ships to a webhook receiver can
  then never carry what the store's own permissions protect. Inbound events from outside keep their payload in a
  separate table (below), never in `events`.

**CloudEvents:** used as the *wire envelope for webhooks only*, not stored. A delivery body is CloudEvents 1.0
structured JSON: `specversion: "1.0"`, `id: "<events_store_id>:<seq>"` (so `source` + `id` is unique, as the spec
requires), `source: "wirecat://store/<events_store_id>"`, `type: "dev.wirecat.task.status"`, `subject: "task:12"`,
`time`, and `data` = the record above ([CloudEvents spec](https://github.com/cloudevents/spec/blob/main/cloudevents/spec.md)).
Locally the shorter record is enough, and NDJSON readers do not need the envelope.

### Commands (shared, in cli-core, so every CLI has them)

| Command | What it does |
|---|---|
| `<tool> events list --since <seq> [--types task.*,memory.*] [--limit 500] --json` | One page: `{ store, head, floor, accounts: "all", events: [...] }`. `head` = the highest seq; caught up when the last seq equals it |
| `<tool> events watch --since <seq\|now> [--types …] [--interval 250] [--exit-on-stdin-eof] --json` | NDJSON until stopped. First line `{"kind":"hello","store":…,"head":…,"floor":…}`, then one line per event, `{"kind":"heartbeat"}` after 20 s of silence |
| `<tool> events server status\|stop\|restart --json` | the events server (below) |
| `<tool> webhooks list\|add\|set\|remove\|test\|deliveries` | webhooks in this tool's config (below) |

- **No profile.** The store is one file for every account; the command reads all of them and says so
  (`accounts: "all"`). It never picks a profile.
- `--since` below `floor` fails with `events_truncated` and `{ since, floor, head }`; the reader reloads in full and
  continues from `head` (beads' 410).
- **A replaced file.** `data_version` on a connection to a file that `store reset` or a restore replaced never moves
  again. `watch` therefore checks the path's device and inode every 2 s, and compares `events_store_id` and `head`
  with what it holds. On any difference it reopens and prints `{"kind":"reset","store":…,"head":…}`; the reader
  reloads in full. A restored backup has the old id but a lower `head`, which is caught the same way.
- **Attach or poll.** When the events server answers on its socket, `watch` subscribes there and prints what it is
  sent; otherwise it polls itself. Its output is the same either way, and the `hello` line says which
  (`"via":"server"` or `"via":"poll"`). If the server goes away mid-stream, `watch` falls back to polling from the
  last seq it printed.
- A polling `watch` holds the file open, so `store reset` refuses while it runs (`quiesce`). The error already names
  the PID. The desktop stops its own watcher before backup, clear and reset (below).
- Runs with `--no-record` from the desktop, as the Memory page's reads already do.

### Desktop

- Rust: a new `events_watch(channel)` command keeps **one** child,
  `<tool> events watch --since now --types task.*,memory.*,fact.*,agent.* --exit-on-stdin-eof --json --no-record`.
  - Any installed tool whose cli-core is new enough. That picks a program, not a profile, so rule 3 holds.
  - Not under the run slot (`run.rs:131-155`), and with a piped stdin, unlike `command()` today, so the child exits
    when the app does.
  - Lines go to the frontend through a `Channel`, the pattern the app already uses. Tauri describes channels as
    "fast and deliver ordered data", and its event system as "not designed for low latency or high throughput"
    ([Tauri docs](https://v2.tauri.app/develop/calling-frontend/#channels)).
  - A failed `send` means the page reloaded. Rust stops the child, and the next mount starts a new one.
  - Rust stops the watcher before backup, clear and `store reset`, and starts it again after.
- Memory page: on `memory.*`, `fact.*` or `agent.*`, re-read the affected list after 300 ms of quiet, then patch rows
  in place. A new row above the viewport shows "2 new", and a click on it scrolls up; the page does not push content
  down (rule 9). While the window is hidden, it only notes that something changed and reloads once when shown.
- Mock: `?events=live` sends `memory.added` after 4 s and `fact.updated` after 8 s; `?events=reset` sends a `reset`.

### The events server

One process per user, for every tool and profile: `<tool> events serve`. It is not the messengers' `serve`, which
holds one messenger connection per profile and stays as it is.

| Question | Answer |
|---|---|
| One or per tool? | **One.** The store is one file for every tool, so one poller and one deliverer are enough; per-tool servers would each poll the same file and race on the same deliveries. Any tool's build can run it: it needs only cli-core |
| Where | `<wirecatDirectory>/server/`: `events.lock` (PID, start time, cli-core version, schema, `events_store_id`), `events.sock` (on Windows the pipe `\\.\pipe\wirecat-events-<user>`), `events.log` (0600, rotated at 5 MB) |
| Who starts it | Any cli-core command that opened the store for writing, at its end, and `mcp serve` at its start. The check is one socket connect (no answer → spawn detached with `--no-record`, the max pattern with an `O_EXCL` starting file and a 30 s grace) and never delays the command's output |
| Who never starts it | A moved run (`isMovedRun` for `WireCat`, or `MESSAGING_STORE` / `WIRECAT_STATE_DIR` set), so tests and throwaway `HOME`s never reach the owner's keyring or a real webhook; `WIRECAT_EVENTS_SERVER=off`; a build older than the one that ships it |
| Health | `events server status --json` connects and asks `hello`: pid, versions, uptime, store id, last seq read, deliveries pending and dead. No answer with a live PID → "not answering"; a stale lock → the next start takes it over |
| Upgrades | A command whose cli-core is **newer** than the running server's asks it to stop and starts its own; an older one leaves a newer server alone, so two installed versions do not take turns |
| Crash | The log and the deliveries are in the store, so nothing is lost; the next writing command starts a new server, and it carries on from the lowest pending delivery |
| Idle | **Never stops on its own** (owner, NEED-5 A). It stops only when asked (`events server stop`, an upgrade, `store reset`) or when the system ends the session (inferred: a logout may end detached processes, depending on the system) |
| After a reboot | Outbound needs nothing: an event exists only because a command ran, and that command started the server. Inbound needs a listener before any command runs, so the owner can turn on "Start at login" (below) |
| `store reset`, backup, restore | `quiesce` first asks the server over its socket to stop, then checks for other holders as today; the next command starts it again. The server also checks the file's inode and store id every 2 s, as `watch` does |
| Keyring | It reads each webhook's secret from the keyring entry of the tool whose config declares it (below). It never writes, deletes or revokes an entry |

#### Start at login

`<tool> events server autostart on|off|status --json`. Any tool can run it; the login item starts
`<that tool> events serve`, and the newer-wins rule above still applies once it runs. What the official docs say
about rights for a per-user login item:

| System | Mechanism | Admin rights? |
|---|---|---|
| Linux | a systemd user unit in `~/.config/systemd/user/`, the "user configuration" unit path ([systemd.unit](https://www.freedesktop.org/software/systemd/man/latest/systemd.unit.html)), enabled with `systemctl --user enable`; the existing `units.ts` code writes such units (`src/background/units.ts:75-96`) | **No** (inferred: the unit lives in the user's own folder and goes to the user's own service manager; the docs say nothing about rights either way) |
| macOS | a LaunchAgent plist in the user's own `Library/LaunchAgents`, which launchd loads for that user ([Apple: Creating launchd jobs](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html)); `units.ts` writes these too (`units.ts:154-214`) | **No** (inferred the same way). macOS 13 and later list it under Login Items, where the owner can turn it off (inferred, not in the docs read) |
| Windows | **Not** Task Scheduler: Microsoft's `schtasks` reference says "Only Administrators can schedule tasks, regardless of the value of the /ru parameter", and an `ONLOGON` task "runs whenever a user (any user) logs on" ([schtasks create](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/schtasks-create)). Instead, a value under `HKEY_CURRENT_USER\Software\Microsoft\Windows\CurrentVersion\Run`, which "makes the program run every time the user logs on"; its command line is at most 260 characters ([Run and RunOnce keys](https://learn.microsoft.com/en-us/windows/win32/setupapi/run-and-runonce-registry-keys)), so it points at a short `.cmd` launcher in the WireCat folder | **No** (inferred: it is the user's own registry hive; the page does not say). The existing per-user schedules run through PowerShell's `New-ScheduledTask*` without asking for admin (`schedules.ts:314-335`), which reads against the `schtasks` sentence; not tried on Windows |

- `status` says `on`, `off` or `broken` (the item points at a program that is gone), the mechanism, and the exact
  command the item runs.
- When `on` cannot finish — no systemd user session (WSL, a distribution without systemd), a policy that blocks the
  key, a Login Items refusal — it changes nothing and answers `{ "done": false, "reason": …, "run": "<the exact
  command>" }`. It never calls `sudo` and never asks for a password (the desktop's rule 6).
- **Desktop:** the Tools page gets one "Events server" block above the tool list (the server is one per user, not
  per tool): its state (running since, version, pending deliveries) and a **Start at login** switch that runs
  `autostart on|off`. When the answer is `done: false`, the switch goes back to off and the block shows why, the
  command to run in a terminal with a Copy button, and "Check again", which runs `autostart status`.
- A moved run refuses `autostart on`: a login item made from a throwaway `HOME` would start a server on the
  owner's real folders.

Inside, it does three things over one connection to the store:

- **Polls** `PRAGMA data_version` every 250 ms and reads new events by seq (measured above).
- **Delivers** each new event to the enabled webhooks whose filters match, then retries what failed.
- **Serves** local subscribers on the socket (JSON lines, `{"subscribe":{"since":…,"types":[…]}}`, as max's socket
  does), and inbound routes on a loopback HTTP port that the Funnel or tunnel points at.

### Webhooks

**Config.** In the tool's own config file, beside `defaults` and `profiles`, because events are store-wide and carry
no account yet:

```json
{
  "webhooks": {
    "ci-bot": { "url": "https://ci.example.com/hooks/wirecat", "events": ["task.*", "memory.added"], "enabled": true }
  }
}
```

- `events` takes the same patterns as `events watch --types`. The secret is never in this file.
- The server finds every tool's file through the CLIs the store records (`clients.ts:70-74`) and cli-base's
  `resolvePaths`, and re-reads a file when it changes.

**Commands** (what the desktop runs; it never edits a config file, rule 1):

| Command | What it does |
|---|---|
| `<tool> webhooks list --json` | name, url, events, enabled, and per webhook the last delivery, pending count, dead count and whether its secret is in the keyring |
| `<tool> webhooks add <name> --url … --events … [--secret-stdin] --json` | writes the entry and stores its secret in the keyring. Both ways work (owner, NEED-7 C): `--secret-stdin` takes the secret the receiving service gave; without it the CLI makes one (32 random bytes, `whsec_`) for the owner to save with `webhooks secret` |
| `<tool> webhooks set <name> [--url …] [--events …] [--enabled true\|false]` | changes the entry |
| `<tool> webhooks secret <name> --to <file>` | writes the secret to a new file at mode 0600, for the receiver to import; never to stdout. `--rotate` makes a new one and keeps the old one valid for 24 h (Standard Webhooks allows several signatures in one header) |
| `<tool> webhooks remove <name>` | removes the entry and the keyring entry |
| `<tool> webhooks test <name>` | sends a signed `dev.wirecat.webhook.test` event now and shows the answer's status |
| `<tool> webhooks deliveries <name> [--dead] --json`, `deliveries retry <id>` | recent deliveries; a dead one sent again |

- `config set webhooks…` refuses and points to `webhooks add`, since an entry without its secret would never sign.
- **Only the owner adds or changes a webhook.** A webhook sends every matching event to a URL, so an agent that could
  add one could copy the owner's activity out. The commands refuse an agent caller, as `config set` does for
  `mcp.authority` (`config-command.ts:179,233-259`). The desktop runs them as the owner.

**Secret.** The keyring entry of the tool whose config holds the webhook: service `<tool>`, account
`webhook:<name>`. I agree with the coordinator's recommendation: one entry per app and webhook, never in the config
file, never printed. The server reads another tool's entry by its service name; it never writes it. What still
needs checking: on macOS, Keychain asks once per program that reads an item, and two tools on two different Node
installs are two programs (inferred, not tried).

**Delivery.**

- Table `webhook_deliveries` (tool, webhook name, seq, attempt, next_attempt_at, lease_until, last_status,
  last_error_code, dead_at). A delivery row is made when the server first reads an event that matches, so a webhook
  added later does not receive the past.
- **Signing: Standard Webhooks.** Headers `webhook-id` (the CloudEvents `id`, the same across retries),
  `webhook-timestamp` (Unix seconds), `webhook-signature: v1,<base64 HMAC-SHA256 of "id.timestamp.body">`; the
  secret is 24–64 random bytes, `whsec_`-prefixed. Only `2xx` is success; a 3xx is a failure; `410 Gone` disables the
  webhook. Retries back off exponentially with jitter over several days (the spec's example starts at once, then
  5 s, 5 min, 30 min, and grows to 24 h, about 75.5 h in total); after the last attempt the delivery is dead and the
  owner is told ([Standard Webhooks spec](https://github.com/standard-webhooks/standard-webhooks/blob/main/spec/standard-webhooks.md)).
- At least once: during an upgrade handover two servers can overlap, so each claims a delivery with a conditional
  `UPDATE … WHERE lease_until < now`, the pattern task claims use (`work-tasks.ts:461-467`). Receivers deduplicate on
  `webhook-id`.
- Timeouts: 10 s per request, at most 4 requests at once, so a slow receiver cannot hold the others.
- Payload size: refs only, well under the spec's advice to stay "smaller than 20kb".

**Desktop: a Webhooks block in each tool's details, beside Permissions.** It lists the tool's webhooks with their
state (delivering, failing since…, dead count), and adds, edits, tests, enables and removes them through the commands
above. Adding offers "Make a secret" or "Paste the secret your service gave"; a pasted one goes to the CLI on stdin.
"Save secret to a file…" opens a save dialog and runs `webhooks secret --to <path>`; the secret never passes
through the page. A mock `?webhooks=<tool>` shows one healthy and one failing webhook.

### Inbound events

- **What reaches the machine:** an HTTPS request through the Tailscale Funnel or Cloudflare tunnel the owner already
  set up for MCP. Funnel listens only on 443, 8443 and 10000 and terminates TLS on the device
  ([Tailscale Funnel](https://tailscale.com/kb/1223/funnel)). `cloudflared` opens only outbound connections
  ([Cloudflare Tunnel](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/)).
  The receiver is the events server's loopback HTTP port, built on the same listener as the MCP HTTP server
  (`src/http/listen.ts:58-73`): `POST /events/in/<source>`, published at its own Funnel path. A machine that is asleep or offline receives nothing, and every source below
  either retries or must be caught up by a sync.
- **Authentication, per source:**

| Source | What it sends | How it is checked | Notes |
|---|---|---|---|
| Telegram bot | the update | `X-Telegram-Bot-Api-Secret-Token`, already supported by `bot watch` (`src/cli/bot/port.ts:146-213`) | webhook and `getUpdates` exclude each other; ports 443, 80, 88, 8443 ([Bot API](https://core.telegram.org/bots/api#setwebhook)) |
| Gmail | only the address and a `historyId` | a Pub/Sub push carries a Google-signed OIDC token: check signature, `aud`, `email`, issuer ([Pub/Sub push auth](https://docs.cloud.google.com/pubsub/docs/authenticate-push-subscriptions)) | `watch` must be renewed at least every 7 days, at most one event per second, some may be lost ([Gmail push](https://developers.google.com/workspace/gmail/api/guides/push)). A **pull** subscription needs no public address (inferred from [Pub/Sub pull](https://docs.cloud.google.com/pubsub/docs/pull), not stated there) |
| Drive | an empty body, headers only | `X-Goog-Channel-Token`, a value we choose | channels expire after at most 1 week for `changes` and are renewed by hand ([Drive push](https://developers.google.com/workspace/drive/api/guides/push)) |
| Other apps | anything | Standard Webhooks signature with a per-source secret in the keyring; timestamp within 5 minutes; `webhook-id` deduplicated | — |

- Gmail and Drive send signals, not content. Their event is `inbound.gmail.changed` / `inbound.drive.changed`, and
  the reaction is the existing sync, so no new reading code is needed.
- A payload that carries content (a bot update, another app's body) goes to an `inbound_events` table shaped like
  `bot_updates`: deduplicated on `(source, external_id)`, payload nulled after 30 days. The `events` row carries
  `ref: "inbound:<id>"` only.

### Notifications to the owner

- **Desktop, while open:** `tauri-plugin-notification`, driven by the same watcher. Per type, the owner chooses one
  of off, a badge on the page, or an OS notification. Defaults: `task.assigned` to the owner and a close suggestion
  waiting for the owner raise a notification; the rest only badge. The text is built on this computer from a fresh
  read ("hermes closed HRB-14"). Limits from the [plugin docs](https://v2.tauri.app/plugin/notification/): on
  Windows it "only works for installed apps", and its actions API is marked mobile-only; the docs say nothing about
  a click on a desktop notification, so opening the task from one is not promised (not tried).
- **Messenger:** a webhook-like entry in a messenger's config, `notify.<name>` with `profile`, `events` and `enabled`;
  the events server runs that messenger's fixed command, `<tool> <profile> notify --event <seq>`, which sends to the
  owner's own chat. The profile is in the entry and was chosen by the owner; there is no default. The
  default text is refs only ("task HRB-14 closed by hermes"); a title needs an explicit opt-in, because it then
  leaves the machine through the messenger.
- The desktop's own notifications need the desktop open; messenger notifications and webhooks need only the server.

### Retention, backups and reset

- Keep 30 days **and** at least the newest 10,000 events, whichever keeps more. Never delete an event that a
  pending delivery still needs. Pruning runs in the existing daily log pruner (`src/store/sqlite/log-pruning.ts`).
  `floor` is the lowest kept seq.
- Size estimate (inferred, not measured): about 100 bytes per row with its index, so 10,000 rows is about 1 MB.
- Backups copy the table with everything else. A reader of a restored file sees `head` lower than its cursor and
  reloads in full (above).
- `store reset` makes a new file with a new `events_store_id` and seq starting at 1; readers reload in full.

## Cross-platform limits (no administrator rights)

| | Linux | macOS | Windows |
|---|---|---|---|
| `data_version` polling | SQLite's own; same everywhere | same | same |
| Events server, started by a command | detached process, Unix socket | the same; socket paths over 103 bytes move to a short folder, as the relay does | detached process, named pipe `\\.\pipe\…` (not a file path) |
| Events server at login | systemd user unit (`units.ts`) | LaunchAgent (`units.ts`) | `HKCU\…\Run` value and a `.cmd` launcher; new code (Task Scheduler at log on needs admin per Microsoft's docs) |
| Desktop notifications | needs a notification service in the session (inferred) | asks the owner once | installed app only (Tauri docs) |
| Inbound | Funnel or tunnel | Funnel needs Tailscale's open-source or standalone variant ([Funnel](https://tailscale.com/kb/1223/funnel)) | Funnel or tunnel |

Not measured on macOS or Windows. Polling avoids file events, which differ most between the systems; the server's
socket is the one part that differs, and `events watch` works without it.

without a server anyway (tests, moved runs, a server that crashed), and the server's start, upgrade and reset rules
