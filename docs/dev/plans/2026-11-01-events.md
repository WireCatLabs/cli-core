# Plan: events and push

Status: design for the owner's review. Nothing here is built. The measurement behind it is in cli-testing
([`performance/events/change-detection`](https://github.com/WireCatLabs/cli-testing/tree/perf/events-change-detection/performance/events/change-detection),
[cli-testing#281](https://github.com/WireCatLabs/cli-testing/pull/281)).

## Why

The owner (2026-11-01): "we need to watch and push changes on change to desktop if it's open. I think we need a
proper push system so the changes can be actually pushed and notifications can come etc. … so it's possible to
subscribe to core events in clis, to the events from outside and so on".

The first need is concrete. WireCat Desktop's Memory page, and the Tasks page its plan describes, must update when
an agent or another CLI changes a task, a memory or a fact. Today the page loads once and has a Refresh button.

After that, the same events must reach:

- other CLIs and agents on this computer;
- other servers and apps, as signed webhooks;
- the owner, as an OS notification or a message in a messenger;
- and the bus must take events *from* outside: Telegram bot updates, Gmail and Drive change signals, other apps.

## Summary

1. **One `events` table in `wirecat.db`, written by SQL triggers** in the same transaction as the change. A trigger
   is part of the database file, so every build of every CLI that writes the migrated store emits events, including
   CLIs released before this one.
2. **An event holds references, never content:** a sequence number, a type (`task.status`), a ref (`task:12`), the
   actor, and the names of the changed fields. Readers fetch current state through the commands they already use.
3. **Local readers poll `PRAGMA data_version` every 250 ms** and read `events WHERE seq > ?`. Measured: 1.3 µs per
   check, no missed commit, about 0.14% of one core. No file watching, no socket, **no daemon**.
4. **`<tool> events watch --since <seq> --json`** prints NDJSON and resumes by sequence. The desktop keeps one such
   child while it is open and forwards lines through a Tauri `Channel`.
5. **Webhooks later, without a daemon:** `events deliver` runs one pass from the existing user-level schedules (and
   continuously while the desktop is open), signs per Standard Webhooks, retries with backoff, and keeps a dead list.

### Prior art: beads

Beads keeps an "events journal": one row per committed mutation, written in the same transaction, with a gapless
`seq`, read by `bd events tail --since <seq> [--follow]` and over HTTP as `GET /v0/beads/events:watch` (server-sent
events, `id: <seq>`, heartbeats every 20 s, a `410` and a `truncated` event when the cursor fell below what pruning
kept) ([events-journal.md](https://github.com/gastownhall/beads/blob/6ebaacba8f5fb1f5005eed0544f26f3a7a58a5e4/docs/reference/events-journal.md)).
Three things carry over:

- **Its push is a poll underneath.** `--follow` "polls once a second", and the HTTP stream re-reads on a jittered
  timer ([events_watch.go](https://github.com/gastownhall/beads/blob/6ebaacba8f5fb1f5005eed0544f26f3a7a58a5e4/internal/httpapi/events_watch.go)).
- **`--exit-on-stdin-eof`** so a desktop parent that dies takes the follower with it.
- **A warning:** each record carries the full issue snapshot, so "publishing the journal publishes the workspace's
  history … editing or deleting a bead does not redact it". This plan keeps content out of the log for that reason.

### Producing events

| Option | Every writer emits? | Old CLI builds emit? | Actor | Cost | Verdict |
|---|---|---|---|---|---|
| **A. No log: the desktop reloads when the store changes** (`data_version` moved) | yes | yes | none | nothing to build in core | **No.** During a sync the store changes on nearly every check: 228 of 405 checks at 50 ms saw a commit with no task event in the measurement. The page would reload all through a sync, and webhooks and resume need a log anyway |
| B. App inserts an event row in each store method, inside `write()` | only paths that remember to; `setStatus` runs outside `write()` | **no**: a tg-cli on an older core writes tasks with no event | exact | one line per write path, about 25 places | No: misses writes by the six CLIs released at different times |
| **C. SQL triggers on the tables that matter** | yes, any connection | **yes**, once any CLI migrates the store | from the row (`task_events.actor_*`, `memories.author_*`, `facts.confirmed_by_*`); none for a bare claim | one migration | **Recommended** |
| D. Extend `task_events` to cover everything | tasks only | yes | yes | — | No: memories and facts are not tasks |
| E. `sqlite3_update_hook` | only the connection that set it | no | — | — | No: the hook belongs to one connection ([SQLite docs](https://www.sqlite.org/c3ref/update_hook.html)); other processes' writes are not reported (inferred from "the database connection identified by the first argument") |

Option C's limit: a trigger cannot learn who acted unless the row says so. A non-TEMP trigger cannot read a
per-connection TEMP table ([CREATE TRIGGER](https://www.sqlite.org/lang_createtrigger.html): "the table to be
modified or queried must exist in the same database"), and an app-defined SQL function would break every older
build that fires the trigger. The rows already carry an actor for the changes that matter most (task events, memory
authors, fact confirmations). Where they do not, `actor` is null and means "unknown", as in beads.

## Recommendation

### The event log

Migration 41 (reserved first in `docs/dev/COORDINATION.md`) adds, additively, with no change to `minCompatible`:

```sql
CREATE TABLE events (
  seq INTEGER PRIMARY KEY AUTOINCREMENT,  -- never reused, even after pruning
  type TEXT NOT NULL,                     -- 'task.status', 'memory.added' …
  subject_type TEXT NOT NULL,             -- 'task' | 'memory' | 'fact' | 'agent_action' | 'inbound'
  subject_id INTEGER NOT NULL,
  actor_type TEXT,                        -- 'person' | 'bot' | null (unknown)
  actor_id INTEGER,
  fields TEXT,                            -- JSON array of changed column names; never values
  at INTEGER NOT NULL                     -- ms
);
```

`AUTOINCREMENT` matters: without it, the rowid of a deleted newest row "might be reused", and a reader's cursor must
never point at a different event ([AUTOINCREMENT](https://www.sqlite.org/autoinc.html)). SQLite lets one writer in
at a time, so `seq` order is commit order: a reader never sees seq 10 while seq 9 is still uncommitted, the gap that
makes outbox cursors hard on Postgres (inferred from the one-writer rule in the [WAL docs](https://www.sqlite.org/wal.html);
AUTOINCREMENT promises increasing numbers, not consecutive ones, so readers never expect `seq + 1`). `store_settings` gets an
`events_store_id`, a random id written once by the migration; it names this file's sequence.

Triggers, each `AFTER … FOR EACH ROW`, and for updates `UPDATE OF <the columns a person sees>` plus
`WHEN old.x IS NOT new.x`, so the folded-name fills, backfills and pruning that run on every writable open
(`src/store/sqlite/open-store.ts:74-88`) do not flood the log:

| Trigger on | Event type | Actor |
|---|---|---|
| `task_events` INSERT | `task.<kind>` (`task.created`, `task.status`, `task.assigned` …); `fields` = the keys of `changes` via `json_each`, never the values | `task_events.actor_*` |
| `tasks` UPDATE OF `claimed_by`, `claimed_until` | `task.claimed` / `task.released` | null (the holder is a free-text name, not an actor) |
| `tasks` UPDATE OF `resolution`, `verdict`, `close_certainty` | `task.updated` with `fields` | null |
| `tasks` DELETE | `task.removed` | null |
| `memories` INSERT / UPDATE OF `body`, `kind`, `status`, `scope`, `subject_*` / DELETE | `memory.added` / `memory.updated` / `memory.removed` | `author_*` on insert |
| `facts` INSERT / UPDATE OF `statement`, `status`, `type`, `project_id` / DELETE | `fact.added` / `fact.updated` / `fact.removed` | `confirmed_by_*` when set |
| `agent_actions` INSERT | `agent.action` | the row's actor |

Notes, reminders, documents, messages and chats are not in the first set. Messages change thousands of times during a
sync and already have their own `changes` read; a message event type would come with its own volume budget later.

### The record a reader sees

```json
{"seq":4212,"type":"task.status","ref":"task:12","actor":"bot:3","fields":["status"],"at":"2026-11-01T10:04:05.120Z"}
```

- `ref` is the same ref every command already takes (`memory:7`, `task:12`). A reader that wants the title runs
  `tasks show task:12`, under its own permissions.
- `fields` tells a page which column to refresh and lets a filter skip noise, without carrying a value.
- **Privacy:** no titles, bodies, statements, message text, URLs or names. A log that ships to a webhook receiver can
  then never carry what the store's own permissions protect. Inbound events from outside keep their payload in a
  separate table (below), never in `events`.

**CloudEvents:** used as the *wire envelope for webhooks only*, not stored. A delivery body is CloudEvents 1.0
structured JSON: `specversion: "1.0"`, `id: "<events_store_id>:<seq>"` (so `source` + `id` is unique, as the spec
requires), `source: "wirecat://store/<events_store_id>"`, `type: "dev.wirecat.task.status"`, `subject: "task:12"`,
`time`, and `data` = the record above ([CloudEvents spec](https://github.com/cloudevents/spec/blob/main/cloudevents/spec.md)).
Locally the shorter record is enough, and NDJSON readers do not need the envelope.

### Commands (shared, in cli-core, so every CLI has them)

| Command | What it does |
|---|---|
| `<tool> events list --since <seq> [--types task.*,memory.*] [--limit 500] --json` | One page: `{ store, head, floor, accounts: "all", events: [...] }`. `head` = the highest seq; caught up when the last seq equals it |
| `<tool> events watch --since <seq\|now> [--types …] [--interval 250] [--exit-on-stdin-eof] --json` | NDJSON until stopped. First line `{"kind":"hello","store":…,"head":…,"floor":…}`, then one line per event, `{"kind":"heartbeat"}` after 20 s of silence |
| `<tool> events subscriptions add <name> --url … --types … [--secret-file <path>]` | slice 4 |
| `<tool> events deliver [--follow]` | slice 4 |
| `<tool> events dead list` / `dead retry <id>` | slice 4 |

- **No profile.** The store is one file for every account; the command reads all of them and says so
  (`accounts: "all"`). It never picks a profile.
- `--since` below `floor` fails with `events_truncated` and `{ since, floor, head }`; the reader reloads in full and
  continues from `head` (beads' 410).
- **A replaced file.** `data_version` on a connection to a file that `store reset` or a restore replaced never moves
  again. `watch` therefore checks the path's device and inode every 2 s, and compares `events_store_id` and `head`
  with what it holds. On any difference it reopens and prints `{"kind":"reset","store":…,"head":…}`; the reader
  reloads in full. A restored backup has the old id but a lower `head`, which is caught the same way.
- `watch` holds the file open, so `store reset` refuses while it runs (`quiesce`). The error already names the PID.
  The desktop stops its own watcher before backup, clear and reset (below).
- Runs with `--no-record` from the desktop, as the Memory page's reads already do.

### Desktop

- Rust: a new `events_watch(channel)` command keeps **one** child,
  `<tool> events watch --since now --types task.*,memory.*,fact.*,agent.* --exit-on-stdin-eof --json --no-record`.
  - Any installed tool whose cli-core is new enough. That picks a program, not a profile, so rule 3 holds.
  - Not under the run slot (`run.rs:131-155`), and with a piped stdin, unlike `command()` today, so the child exits
    when the app does.
  - Lines go to the frontend through a `Channel`, the pattern the app already uses. Tauri describes channels as
    "fast and deliver ordered data", and its event system as "not designed for low latency or high throughput"
    ([Tauri docs](https://v2.tauri.app/develop/calling-frontend/#channels)).
  - A failed `send` means the page reloaded. Rust stops the child, and the next mount starts a new one.
  - Rust stops the watcher before backup, clear and `store reset`, and starts it again after.
- Memory page: on `memory.*`, `fact.*` or `agent.*`, re-read the affected list after 300 ms of quiet, then patch rows
  in place. A new row above the viewport shows "2 new", and a click on it scrolls up; the page does not push content
  down (rule 9). While the window is hidden, it only notes that something changed and reloads once when shown.
- Mock: `?events=live` sends `memory.added` after 4 s and `fact.updated` after 8 s; `?events=reset` sends a `reset`.

### Remote subscribers (webhooks)

- Tables: `event_subscriptions` (name, url, types, deliverer tool, state, created_at, disabled_reason) and
  `event_deliveries` (subscription, seq, attempt, next_attempt_at, lease_until, last_status, last_error_code).
- **Who delivers, without a daemon:** `events deliver` runs one pass and exits. Three things run it:
  - a user-level schedule every minute, using the existing systemd, launchd and Task Scheduler code
    (`src/background/schedules.ts:361-364`);
  - the desktop, continuously while it is open (`--follow`);
  - optionally, a `serve` that is already running.
  Several deliverers are safe together: each claims a delivery with a conditional `UPDATE … WHERE lease_until < now`,
  the pattern task claims use (`work-tasks.ts:461-467`). Delivery is at least once; receivers deduplicate on
  `webhook-id`.
- **Signing: Standard Webhooks.** Headers `webhook-id` (the CloudEvents `id`, the same across retries),
  `webhook-timestamp` (Unix seconds), `webhook-signature: v1,<base64 HMAC-SHA256 of "id.timestamp.body">`; the
  secret is 24–64 random bytes, `whsec_`-prefixed. Only `2xx` is success; a 3xx is a failure; `410 Gone` disables the
  subscription. Retries back off with jitter (the spec's example: at once, 5 s, 5 min, 30 min, 2 h, 5 h, 10 h, 10 h);
  after the last attempt the delivery goes to the dead list and the owner is told
  ([Standard Webhooks spec](https://github.com/standard-webhooks/standard-webhooks/blob/main/spec/standard-webhooks.md)).
- Filters: `types` patterns per subscription (`task.*`, `memory.added`). Per-account filters wait until events carry
  an account.
- **Secrets:** never printed. `add` either reads the receiver's secret from a file the owner names
  (`--secret-file`, mode 0600 checked) or generates one and writes it to that file for the receiver to import. The
  value goes into the keyring of the tool that owns the subscription (`events:<subscription name>`), and only that
  tool delivers it (NEED-2).
- Payload size: refs only, so well under the spec's advice to stay "smaller than 20kb".

### Inbound events

- **What reaches the machine:** an HTTPS request through the Tailscale Funnel or Cloudflare tunnel the owner already
  set up for MCP. Funnel listens only on 443, 8443 and 10000 and terminates TLS on the device
  ([Tailscale Funnel](https://tailscale.com/kb/1223/funnel)). `cloudflared` opens only outbound connections
  ([Cloudflare Tunnel](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/)).
  The receiver is a route on the HTTP listener the tool already runs (`src/http/listen.ts:58-73`):
  `POST /<tool>/events/in/<source>`. A machine that is asleep or offline receives nothing, and every source below
  either retries or must be caught up by a sync.
- **Authentication, per source:**

| Source | What it sends | How it is checked | Notes |
|---|---|---|---|
| Telegram bot | the update | `X-Telegram-Bot-Api-Secret-Token`, already supported by `bot watch` (`src/cli/bot/port.ts:146-213`) | webhook and `getUpdates` exclude each other; ports 443, 80, 88, 8443 ([Bot API](https://core.telegram.org/bots/api#setwebhook)) |
| Gmail | only the address and a `historyId` | a Pub/Sub push carries a Google-signed OIDC token: check signature, `aud`, `email`, issuer ([Pub/Sub push auth](https://docs.cloud.google.com/pubsub/docs/authenticate-push-subscriptions)) | `watch` must be renewed at least every 7 days, at most one event per second, some may be lost ([Gmail push](https://developers.google.com/workspace/gmail/api/guides/push)). A **pull** subscription needs no public address (inferred from [Pub/Sub pull](https://docs.cloud.google.com/pubsub/docs/pull), not stated there) |
| Drive | an empty body, headers only | `X-Goog-Channel-Token`, a value we choose | channels expire after at most 1 week for `changes` and are renewed by hand ([Drive push](https://developers.google.com/workspace/drive/api/guides/push)) |
| Other apps | anything | Standard Webhooks signature with a per-source secret in the keyring; timestamp within 5 minutes; `webhook-id` deduplicated | — |

- Gmail and Drive send signals, not content. Their event is `inbound.gmail.changed` / `inbound.drive.changed`, and
  the reaction is the existing sync, so no new reading code is needed.
- A payload that carries content (a bot update, another app's body) goes to an `inbound_events` table shaped like
  `bot_updates`: deduplicated on `(source, external_id)`, payload nulled after 30 days. The `events` row carries
  `ref: "inbound:<id>"` only.

### Notifications to the owner

- **Desktop, while open:** `tauri-plugin-notification`, driven by the same watcher. Per type, the owner chooses one
  of off, a badge on the page, or an OS notification. Defaults: `task.assigned` to the owner and a close suggestion
  waiting for the owner raise a notification; the rest only badge. The text is built on this computer from a fresh
  read ("hermes closed HRB-14"). Limits from the [plugin docs](https://v2.tauri.app/plugin/notification/): on
  Windows it "only works for installed apps", and click actions are mobile-only, so a click cannot open the task.
- **Messenger:** a subscription whose target is `<tool> <profile> send` to the owner's own chat, run by
  `events deliver`. The profile is stored on the subscription and was chosen by the owner; there is no default. The
  default text is refs only ("task HRB-14 closed by hermes"); a title needs an explicit opt-in, because it then
  leaves the machine through the messenger.
- Nothing notifies while the desktop is closed unless the owner adds a messenger or webhook subscription.

### Retention, backups and reset

- Keep 30 days **and** at least the newest 10,000 events, whichever keeps more. Never delete an event that a
  pending delivery still needs. Pruning runs in the existing daily log pruner (`src/store/sqlite/log-pruning.ts`).
  `floor` is the lowest kept seq.
- Size estimate (inferred, not measured): about 100 bytes per row with its index, so 10,000 rows is about 1 MB.
- Backups copy the table with everything else. A reader of a restored file sees `head` lower than its cursor and
  reloads in full (above).
- `store reset` makes a new file with a new `events_store_id` and seq starting at 1; readers reload in full.

## Cross-platform limits (no administrator rights)

| | Linux | macOS | Windows |
|---|---|---|---|
| `data_version` polling | SQLite's own; same everywhere | same | same |
| Webhook schedule | systemd user timer | launchd agent | Task Scheduler for the current user (inferred: no admin needed for a task of one's own) |
| Desktop notifications | needs a notification service in the session (inferred) | asks the owner once | installed app only (Tauri docs) |
| Inbound | Funnel or tunnel | Funnel needs Tailscale's open-source or standalone variant ([Funnel](https://tailscale.com/kb/1223/funnel)) | Funnel or tunnel |

Not measured on macOS or Windows. Polling avoids sockets, pipes and file events, which are where the three systems
differ.

## Open questions

- **NEED-1 · Who sends webhooks when no desktop is open?** A: a user-level schedule every minute, plus the desktop
  while it is open (latency up to a minute when it is closed). B: every long-running process (`serve`, HTTP MCP)
  delivers under a lease; nothing when none runs. C: a new `events serve` daemon. Recommended **A**: no daemon, and
  the schedule code exists on all three systems.
- **NEED-2 · Where is a webhook secret kept, given that keyring entries are per tool but subscriptions live in the
  shared store?** A: in the keyring of the tool that created the subscription; only that tool delivers it. B: a new
  shared keyring service `wirecat` that every CLI reads. C: a 0600 file in the shared state folder. Recommended
  **A**: it follows the existing one-entry-per-app rule. The cost: a subscription stops when its tool is uninstalled,
  and `subscriptions list` says so.
- **NEED-3 · Do task claims get an actor?** Today a claim writes no `task_events` row, so `task.claimed` has no
  actor. A: leave it null. B: `claim` and `release` write a `task_events` row (new kinds `claimed`, `released`), and
  the `tasks` trigger is dropped. Recommended **B** in the same cli-core release: the Agents page and the audit trail
  both want to know who claimed. Older builds' claims then emit nothing until those CLIs update.
- **NEED-4 · What leaves the machine in a messenger notification?** A: refs only. B: the task title or memory body
  too, after an explicit opt-in per subscription. Recommended **A** by default, with **B** as the opt-in.
- Message and chat events: which ones, and at what volume budget (not in slice 1).
- Inbound payloads from other apps: whether any should become tasks or memories directly, or only events.
